# agones-lite 企画書

この文書は、agones-lite を何のために作り、どこまでを作るのかを定める。
作り方は [設計書](design.md) に書く。

## 背景

[Agones](https://github.com/agones-dev/agones) は、専用ゲームサーバを Kubernetes の上で運用するための仕組みである。
ゲームサーバの起動、待機プールの維持、マッチメイカからの割り当て、自動スケールを、Kubernetes の拡張として提供する。

Agones を使うには Kubernetes クラスタが要る。
数台の VM で足りる規模のゲームにとって、クラスタの構築と運用はゲームサーバ本体より重い仕事になりやすい。

Agones には Kubernetes なしで動く「ローカルモード」があるが、これは開発用の模擬である。
1 台分の SDK 応答をメモリ上で返すだけで、ゲームサーバの起動、待機プール、割り当ては行わない。
つまり現状では、Kubernetes を持たないチームが Agones の仕組みで本番運用する手段がない。

## 目的

agones-lite は、Agones の中核機能を Kubernetes なしで動かすアプリケーションサーバである。
Kubernetes が担っていた仕事のうち、ゲームサーバの運用に必要な部分だけを自前で持つ。

対象は、VM 1 台から数台でゲームサーバを本番運用する個人や小規模チームである。
開発機でも同じものが動くので、手元で待機プールから割り当てまでを試す用途にも使える。

## Agones の資産がそのまま使えること

agones-lite は、Agones 向けに作られたものを書き換えずに受け入れる。
対象は次の 3 つである。

- **ゲームサーバ**：公式 SDK を組み込んだゲームサーバのコンテナイメージが、無改造で動く。
- **定義ファイル**：GameServer、Fleet、FleetAutoscaler の YAML を、対応範囲内でそのまま適用できる。
- **割り当てクライアント**：Agones の allocator サービス向けに書かれたクライアントが、接続先を変えるだけで動く。

この互換性があるので、agones-lite で始めたゲームは、規模が大きくなったら Agones に移れる。
逆に、Agones で動いているゲームの小さな環境を agones-lite で立てることもできる。

互換の基準にする Agones のバージョンは v1.62.0 に固定する。
リポジトリには同じバージョンを `third_party/agones` に submodule として置き、設計と実装の参照元にする。

## v1 の範囲

v1 には次の機能を含める。

| 機能 | 内容 |
|---|---|
| GameServer | 起動、ポート割り当て、SDK、ヘルスチェック、終了までのライフサイクル |
| Fleet | 同じ仕様のゲームサーバを指定台数だけ維持する。仕様変更時の入れ替え（Recreate、RollingUpdate）を含む |
| Allocation | 待機中のゲームサーバを 1 台選んで割り当て、接続先を返す |
| FleetAutoscaler | Fleet の台数を自動で調整する。Buffer、Counter、List、Webhook、Schedule、Chain の各ポリシー |
| Counters と Lists | ゲームサーバごとの数値カウンタとリスト。SDK、Allocation、FleetAutoscaler から使える |
| 複数ノード | コントロールプレーン 1 台と、ノードエージェント複数台の構成。1 台に同居させることもできる |
| ノードの保守 | 新規配置の停止（cordon）と退避（drain） |
| 可観測性 | Prometheus メトリクス、イベント履歴、ゲームサーバのログ取得 |

## やらないこと

次のものは v1 でも、その後でも作らない。

- kubectl、Helm、CRD との互換
- コントロールプレーンの冗長化
- 複数クラスタにまたがる割り当て（要求されたらエラーを返す）
- Agones で Alpha または Dev 段階の機能（PlayerTracking、PlayerAllocationFilter、Wasm による自動スケール、ProcessorAllocator、RollingUpdateSurge）
- GKE Autopilot 向けの機能と PodDisruptionBudget
- Windows コンテナのゲームサーバ
- Web の管理画面
- VM そのものの増減（クラウドの自動スケールとの連携）
- initContainers と、configMap や secret を使うボリューム

次のものは v1 には含めないが、後で検討する。

- OpenTelemetry によるトレース
- 開発用 GameServer（手元で動かしているプロセスを登録する機能）
- Docker 以外の実行基盤（OS プロセスを直接起動する方式など）

## 想定する規模と環境

設計が余裕をもって満たすべき上限を、次のとおり置く。

| 項目 | 目安 |
|---|---|
| ノード | 10 台 |
| ゲームサーバ | 合計 1,000 台 |
| Allocation | 毎秒 50 件 |

本番の対象は Linux（amd64 と arm64）とする。
macOS（Docker Desktop や Colima）は開発用として動作を保証するが、ノードの資源容量の扱いは簡易にとどめる。

各ノードには Docker が必要である。
ゲームサーバは Docker コンテナとして動く。

## 本家 Agones との関係

agones-lite は Agones の非公式な派生であり、Agones のプロジェクトとは関係がない。
README にその旨を明記する。

ライセンスは Agones と同じ Apache-2.0 とする。
Agones のコードを参照して書いた箇所には出典を記す。

Agones の Go モジュール（`agones.dev/agones` v1.62.0）は、ビルドの依存として取り込む。
使うのは、リソースの型とそのメソッド（既定値の付与、検証、セレクタの照合、カウンタとリストの操作）、および SDK と Allocation の生成コードである。
制御ロジックは Kubernetes のクライアントに深く依存しているため流用せず、参照して書き直す。

## 読み物として楽しめるコード

agones-lite のコードは、作者自身が読んで楽しめることを要件にする。
Agones の仕組みを、Kubernetes の知識なしに上から下へ読める形で書き直すことが、この企画のもう一つの成果物である。

そのために次のことを守る。

- 関数の認知的複雑度（cognitive complexity）を 10 以下にする。
- 関数の長さは 50 行、ネストの深さは 3 段を目安にする。
- 上の 3 つは lint で検査し、CI で違反をビルド失敗にする。
- コメントは英語で、簡潔に書く。
- パッケージの名前と分け方を Agones に揃え、`third_party/agones` と並べて読み比べられるようにする。
- 設計書に「コードの読み方」の章を置き、読む順番と Agones の対応箇所を示す。

## v1 の完成条件

次の 8 つをすべて満たしたとき、v1 を完成とする。

1. Agones のサンプルである simple-game-server のイメージが、無改造で起動して Ready になる。
2. Agones のリポジトリにある Fleet と FleetAutoscaler のサンプル YAML が、対応範囲内でそのまま適用できる。
3. 公式 SDK（gRPC と REST）から呼んだ stable と beta の全 RPC が、Agones と同じ応答を返す。
4. Agones の allocator 向けのクライアントが、接続先の変更だけで Allocation できる。
5. 2 ノード構成で片方を止めても、割り当て前のゲームサーバは他方で補充され、割り当て済みのゲームサーバは保護される。
6. コントロールプレーンとエージェントを再起動しても、稼働中のゲームサーバが止まらない。
7. 10 ノード、1,000 台、毎秒 50 件の目安を、疑似ノードを使った負荷試験で満たす。
8. すべてのコードが lint を通る。

## 実装の順序

まず 1 台で端から端まで動かし、その後に複数ノードへ広げる。
各段階の終わりに、動くものが手に入る。

| 段階 | 作るもの | 終わったときにできること |
|---|---|---|
| M1 | GameServer と SDK（同居モード） | YAML を適用するとゲームサーバが起動し、SDK で Ready になり、Shutdown で消える |
| M2 | Fleet と Allocation | 待機プールを維持し、割り当て API で 1 台を取り出せる |
| M3 | Counters と Lists、FleetAutoscaler | 複数セッション型のサーバを扱え、台数が自動で増減する |
| M4 | エージェントの分離、認証、障害時の処理、cordon と drain | 複数の VM で運用でき、ノードの停止と保守に耐える |
| M5 | 可観測性と仕上げ | メトリクス、イベント、ログが揃い、完成条件を満たす |

コントロールプレーンとエージェントの境界は M1 から切っておく。
M1 から M3 では両者を同じプロセスの中で直接つなぎ、M4 でネットワーク越しの接続に置き換える。

## リスク

**Agones の内部 API への依存**：取り込む型とメソッドは Agones の公開 API ではなく、バージョン間で変わりうる。
v1.62.0 に固定して使い、上げるときは差分を確認してから上げる。

**Kubernetes の型ライブラリの重さ**：Agones の型は Kubernetes の型ライブラリに依存しているため、本体のバイナリにそれが含まれる。
クラスタは要らないが、バイナリの大きさとビルド時間は増える。
ゲームサーバごとに常駐する sidecar は、この依存を含まない別のバイナリにする。
依存の実際の重さは M1 の最初に計測し、許容できなければ型を自前で定義する方針に切り替える。

**複雑度の上限と機能の広さの両立**：v1 の範囲は広く、Fleet の入れ替えや自動スケールの計算は Agones でも大きな関数になっている。
制御ロジックを「現在の状態から操作の一覧を求める純粋関数」と「操作を実行する薄い層」に分けることで、複雑度 10 以下を保つ。
それでも収まらない箇所が出たら、機能を削るのではなく、データの持ち方を見直す。

**SDK の細かい挙動の差**：ワイヤ互換は、メッセージの形だけでなく、応答の順序やタイミングにも及ぶ。
公式 SDK のクライアントから全 RPC を叩く適合テストを M1 から用意し、差を早く見つける。

**名称**：名前に Agones を含むため、公式のプロジェクトと誤解されるおそれがある。
README の冒頭に非公式であることを書く。

## 決定の記録

この企画と設計は、質問と回答を 7 回くり返して決めた。
決定の一覧を次に示す。

### 企画

| 論点 | 決定 |
|---|---|
| 目的 | Kubernetes なしの小規模本番運用（VM 1 台から数台） |
| 規模の目安 | 10 ノード、1,000 台、毎秒 50 件の割り当て |
| v1 の範囲 | GameServer、Fleet、Allocation、FleetAutoscaler、Counters と Lists |
| 自動スケールのポリシー | Buffer、Counter、List、Webhook、Schedule、Chain（Wasm は作らない） |
| ライセンスと公開 | Apache-2.0 で公開。README は英語で、非公式と明記する |
| 成果物の文書 | `docs/planning.md` と `docs/design.md`（日本語） |
| 実装の順序 | 1 台で端から端まで動かしてから、複数ノードに広げる |

### 構成

| 論点 | 決定 |
|---|---|
| 実装言語 | Go |
| プロセス構成 | コントロールプレーン 1 台とノードエージェント複数台。同じプロセスに同居できる |
| 実行基盤 | Docker コンテナ |
| SDK サーバの置き場所 | ゲームサーバごとの sidecar コンテナ。ネットワーク名前空間を共有する |
| sidecar の通信先 | 同じノードのエージェント。エージェントがコントロールプレーンに中継する |
| ノード間の通信 | エージェントからコントロールプレーンへ接続し、あるべき状態を購読する |
| 状態の保存 | SQLite（単一ファイル） |
| バイナリ | 本体 1 つ（コントロールプレーン、エージェント、CLI）と sidecar 1 つ |
| 配布 | 本体はバイナリと systemd のユニット例。sidecar はコンテナイメージ |
| 対応 OS | Linux を本番、macOS を開発用とする |

### 互換性

| 論点 | 決定 |
|---|---|
| SDK | 完全なワイヤ互換（gRPC、REST、WebSocket） |
| 定義ファイル | Agones 互換のサブセット |
| 未対応のフィールド | 無視しても実行内容が変わらないものは警告して無視し、変わるものは拒否する |
| namespace | 名前の区画として保持する。権限の分離には使わない |
| Allocation の API | Agones の allocator 互換（gRPC と REST） |
| 管理 API | 独自の REST/JSON と専用の CLI。kubectl 互換は目指さない |
| 外部 API の認証 | TLS とトークン。Allocation はクライアント証明書も使える |
| ノードの参加 | 参加トークン。トークンに CA の指紋を含める |
| Agones のコードの流用 | 型と生成コードを Go モジュールとして取り込む。制御ロジックは書き直す |
| submodule | `third_party/agones` を v1.62.0 に固定。参照用で、ビルドには使わない |

### 挙動

| 論点 | 決定 |
|---|---|
| 状態と遷移 | Agones と同じ 11 種類の状態と遷移 |
| ポートポリシー | Static、Dynamic、Passthrough、None。ノードごとにポート範囲を持つ（既定 7000 から 8000） |
| ヘルス判定 | sidecar が Agones と同じ閾値で判定する。開始の合図は initialDelaySeconds の経過とする |
| コンテナの終了 | 終了コード 0 は Shutdown、それ以外は Unhealthy。自動再起動はしない |
| ノードの選び方 | CPU とメモリの要求量、ノードごとの台数上限、Packed または Distributed |
| 空きが足りないとき | Error にせず、空きが出るまで配置を待つ |
| Fleet の更新 | Recreate と RollingUpdate。maxSurge と maxUnavailable の既定は 25% |
| Allocation の実行 | 1 本の直列処理。Agones のバッチ機構は持たない |
| ノードとの接続が切れたとき | 割り当て前のゲームサーバは 5 分後に失われたものとして補充する。割り当て済みは 24 時間まで復帰を待つ |
| コントロールプレーンの停止 | 稼働中のゲームサーバは動き続け、新規の割り当てとスケールだけが止まる |
| エージェントの再起動 | 稼働中のコンテナを止めずに引き取り直す |
| feature gate | 仕組みを持たない。v1.62.0 で既定で有効な挙動に固定する |

### 実装の方針

| 論点 | 決定 |
|---|---|
| 制御ロジックの構造 | 純粋関数と薄い実行層に分ける |
| パッケージ構成 | Agones の構成に対応させる |
| 品質の検査 | 複雑度 10 以下、関数長 50 行、ネスト 3 段を lint で検査し、CI で必須にする |
| コメント | 英語で簡潔に書く |
| 読むための案内 | 設計書の「コードの読み方」の章と、各パッケージ冒頭の概要 |
| 管理 API のプロトコル | REST/JSON のみ。変更の購読は Server-Sent Events |
| テスト | 純粋ロジックの単体テスト、SDK の適合テスト、実際の Docker での結合テスト、障害注入テスト |
| 依存 | 最小限にする。CLI は標準の flag、ログは標準の slog、SQLite は cgo の要らないドライバ |
| CI と図 | GitHub Actions、Mermaid |
| モジュール名 | `github.com/ponyo877/agones-lite` |
